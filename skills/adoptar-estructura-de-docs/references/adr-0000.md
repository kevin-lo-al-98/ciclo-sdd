# Usar MADR para registrar las decisiones de arquitectura

## Context and Problem Statement

Las decisiones de arquitectura del proyecto se toman en conversaciones y se olvidan. El
código conserva qué se hizo, pero no por qué se descartaron las alternativas, y esa
ausencia lleva a deshacer decisiones acertadas o a repetir errores ya evaluados. Hace
falta un formato ligero y estándar para dejar constancia del porqué.

## Considered Options

* MADR 4.0
* ADR en formato Nygard
* Sin formato: notas libres en el README

## Decision Outcome

Chosen option: "MADR 4.0", because es un formato estándar y mantenido, con secciones
opcionales que permiten desde una decisión pequeña hasta una con análisis completo, y
porque incluye las alternativas descartadas, que el formato de Nygard no exige.

### Consequences

* Good, because cada decisión importante queda con su contexto y sus alternativas
* Good, because el formato es conocido y las herramientas que lo leen funcionan sin
  adaptarlo
* Bad, because escribir un ADR cuesta tiempo en cada decisión, y una decisión trivial
  registrada por costumbre entierra las importantes

### Confirmation

En la revisión de cada PR que cambie la estructura, las dependencias o una convención
del proyecto se comprueba si falta el ADR correspondiente.

## More Information

Los ADRs viven en `docs/decisions/` y se numeran `NNNN-titulo-con-guiones.md`. Un ADR
aceptado no se reescribe: se crea uno nuevo que lo sustituya y el anterior pasa a
`superseded by ADR-NNNN`.
